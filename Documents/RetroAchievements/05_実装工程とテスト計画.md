# 実装工程とテスト計画

実際の確認担当、macOSキーチェーン、GUI操作、ユーザー受入、完了報告の運用は
[44_動作確認運用手順.md](44_動作確認運用手順.md)を規範とする。

## 1. 実装方針

- 実装順序は`macOS -> Windows -> Linux -> Android`で固定する。
- macOSでRA全機能と受入試験を完了し、その実装を後続OSの挙動基準とする。
- 各OSはRA全機能とRA対応buildのRA mode OFFによるNormal回帰を完了するまで次のOSへ進まない。
- 未着手OSではRAを有効化せず、既存Normal buildを維持する。
- 後続OS向けstub、仮実装、未検証buildは前工程の完了条件に含めない。
- OS固有問題の修正で共通コードを変更した場合、対応済みの全OSで回帰試験を行う。
- 共通コード変更とOS固有移植は別コミットにする。
- 各Phaseは原則として1つ以上の独立コミットに分け、失敗を残して次へ進まない。
- 新規コードは`Source/RA/`へ集約し、既存`Source/UI`とVMへの変更を接続点に限定する。
- 配布・検証対象はRA対応buildに一本化し、コンパイル時RA無効buildをテスト対象にしない。

macOSは実装上の基準であり、仕様の優先順位を変更しない。macOS固有の都合を
Windows、Linux、Androidへ適用できない場合は、各仕様書に従ってOS固有アダプタで
吸収する。共通仕様を変更する必要がある場合は、先に本仕様書群を更新する。

## 3. OS工程ゲート

### 3.1 開始条件

| 対象OS | 開始条件 |
|---|---|
| macOS | Phase 0の基準線記録が完了している |
| Windows | macOS Phase 8が完了している |
| Linux | Windows Phase 9とmacOS再試験が完了している |
| Android | Linux Phase 10とmacOS・Windows再試験が完了している |
| 全OS最終受入 | Android Phase 11と全対応済みOSの再試験が完了している |

### 3.2 共通コード変更時の扱い

`Source/RA/`のplatform非依存部分、VM接続点、D88処理、state形式、DB schema、
オーバーレイ共通部、同梱依存物を変更した場合は共通コード変更とみなす。

1. OS固有変更とは別コミットにする。
2. 変更理由と影響する仕様をPhase記録へ残す。
3. 変更を必要としたOSで対象試験を実行する。
4. 既に完了した全OSでRA対応build、RA自動試験、RA mode OFFのNormal回帰を再実行する。
5. 再試験が完了するまで、そのOSのPhaseを完了扱いにしない。

### 3.3 HTTP backend共通適合試験

各OSのHTTP実装へ同じtest vectorを適用する。

- GET、空POST、通常POST、content type、User-Agent。
- 200、204、4xx、5xx、空body、8MiB境界、上限超過。
- DNS、TLS、connect timeout、total timeout、cancel、shutdown。
- API redirect拒否、画像HTTPS redirect、HTTPSからHTTPへのredirect拒否。
- gzip展開後上限、破損encoding、破損JSON、不正UTF-8。
- cancelとnetwork完了のraceでterminal completionとserver callbackが各1回だけであること。

## 6. Phase 2: macOSメモリとハッシュ

作業:

- `PC88`と`VM`へ副作用のないRAメモリ読出しAPIを追加する。
- 保存管理用whole-file MD5、bank別RA識別hash、D88解析を行う`RaMediaProbe`を追加する。
- `rcheevos`のPC8800ハッシュ結果との比較テストを作る。

テスト:

- RAM先頭・末尾、TVRAM先頭・末尾。
- RAMからTVRAMへまたぐ連続読出し。
- TVRAM末尾から範囲外へまたぐ読出し。
- 完全範囲外、null buffer、0 byte。
- 1 bank D88では保存管理用MD5とRA識別hashが同じこと。
- multi-bank D88では保存管理用whole-file MD5とbank別RA識別hashが異なり得ること。
- bank選択値に応じてRA識別hashが変わること。
- ファイル途中変更、truncated D88、0 byte、過大サイズ。
- 現行`ProbeD88Image()`が許容する末尾padding・未解釈suffixで受理結果とbank数が一致すること。

完了条件:

- 同じfixtureをXM8と`rcheevos`へ渡したMD5が一致する。
- メモリ読出しでVM状態が変化しない。
- macOSのNormal回帰試験が成功する。

## 16. 共通OS受入シナリオ

各OSの完了Phaseでは、利用可能な全入力方式を使って次を実行する。Android固有項目は
Phase 11で追加実施する。

1. Normalで既存D88を起動・書込み・終了し、従来動作を確認する。
2. RA Softcoreで未登録D88を直接開き、自動登録から解除通知まで確認する。
3. RA Hardcoreで禁止操作を全入力入口から試す。
4. multi-bank D88をbank切替し、RAセッションが維持されることを確認する。
5. M3Uの複数D88を交換し、同一Game IDのmedia changeを確認する。
6. Drive 2の補助媒体を交換し、RA active mediaが変わらないことを確認する。
7. 起動前offline、実行中切断、再接続を確認する。
8. 原本を外部で変更し、既存媒体と混同されないことを確認する。
9. バッジ、複数Challenge、Progress、複数Leaderboard tracker、通知を同時発生させ、動的ステータス行が
   通知を優先し、終了後に継続pageを3秒ごとに1件ずつ表示することを確認する。
10. RA対応buildのRA mode OFFでRA通信やRA session変更が発生しないことを確認する。
11. DBまたは作業コピー生成失敗時に原本D88を直接開かないことを確認する。
12. 旧Normal stateをRAモードで拒否し、Normalでは従来どおり読めることを確認する。
13. 1回の音声buffer生成で複数frameが進んでも全frameの実績評価が行われることを確認する。

## 17. Phase 12: 全OS最終受入

### 17.1 自動test matrix

| 順序 | Platform | Build | Tests |
|---:|---|---|---|
| 1 | macOS | x86_64/arm64、RA対応Debug/Release | ctest、RA unit/integration、RA mode OFF回帰 |
| 2 | Windows | Win32/x64/ARM64、RA対応Debug/Release | RA unit/integration、RA mode OFF回帰 |

| 4 | Android | RA対応Debug/Release、対象ABI | JVM/JNI、native、instrumented smoke、RA mode OFF回帰 |

最終受入でも表の順番に実行する。途中で共通コードを修正した場合はmacOSから
やり直す。OS固有コードだけの修正は当該OSを再実行し、その変更が他OSのbuild定義や
配布物へ影響しないことを確認する。

### 17.2 最終受入条件

- NormalのD88、M3U、bank、state、Full Speedに回帰がない。
- RAモード起動前後で原本D88のMD5が不変である。
- 同じ既知D88から4 OSで同じMD5とRA Game IDを得る。
- Main RAMとText VRAMの実績が正しく評価される。
- Softcore stateがRA progressを含めて復元される。
- RA stateとNormal stateが別pathであり、旧stateをRAモードで安全に拒否する。
- Hardcore禁止操作に迂回経路がない。
- D88本体、password、token、ローカル絶対パスをサーバーまたはログへ漏らさない。
- Android API 19向け静的検証が成功し、API 22とAPI 36で起動、ログイン、
  ライブラリ、ゲーム開始が完了する。
- RAサーバー障害時もOffline sessionとしてゲームを実行できる。
- 全OSでAchievement、Challenge、Leaderboard、Rich Presence、画像、ライブラリが
  同じ仕様で動作する。
