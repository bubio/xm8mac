# 要件とアーキテクチャ

## 1. 対象範囲

### 1.1 初期リリースに含める機能

- ユーザー名・パスワードによるログインとトークン再ログイン
- D88のRAゲーム識別
- 実績一覧、解除、進捗、バッジ
- Challenge Indicator
- Rich Presence
- Leaderboardの開始、失敗、送信、結果
- SoftcoreとHardcore
- RA接続状態、切断、再接続、サーバーエラー
- D88/M3U/フォルダ取り込みを備えたゲームライブラリ
- Windows、macOS、Linux、AndroidのSDLオーバーレイ

### 1.2 対象外

- 実績の作成・編集・デバッグ機能
- RA開発者向けコードノート
- D88以外の新規媒体形式
- D88バイナリのアップロード
- 複数RAアカウントの同時保持
- オフライン中の解除を後からRAへ送信する機能
- RA Webサイトの埋め込み表示
- クラウドセーブ同期

## 2. 実行モード

```text
Normal
  └─ RAを使用しない既存動作

RA
  ├─ Softcore
  └─ Hardcore
```

実行中の有効モードは`RaRunMode`列挙型として定義する。

```cpp
enum class RaRunMode {
    Normal,
    Softcore,
    Hardcore
};
```

永続設定は実行モードを直接1値で保存せず、次の2値をRAライブラリDBへ保存する。

```cpp
enum class RaAchievementMode {
    Softcore = 1,
    Hardcore = 2
};

struct RaModeSettings {
    bool enabled;                 // 初期値false
    RaAchievementMode last_mode; // SoftcoreまたはHardcore、初期値Softcore
};
```

- `enabled=false`なら実行モードは`Normal`、trueなら`last_mode`を使う。
- RAをOFFにしても`last_mode`は変更しない。
- RA未ビルド時は常に`Normal`として動作する。
- RAゲーム実行中のモード変更は予約せず、現在のセッション終了を要求する。
- `Hardcore`から`Softcore`へ落とす操作も、そのセッションを終了して再起動する。
- RA設定を既存`setting.bin`へ追加しない。

## 3. コンポーネント

### 3.1 `RaService`

RA機能のファサードであり、`rc_client_t`を1つだけ所有する。

責務:

- 初期化、終了、ログイン、ログアウト
- ゲーム識別、セッション開始、媒体変更、アンロード
- `rc_client_do_frame()`と`rc_client_idle()`の呼び分け
- `rc_client_event_t`をXM8内部イベントへ変換
- Softcore/Hardcore設定の`rc_client`への反映
- オフラインセッションへの確定遷移
- PC-8000/8800 hash library、game title、ユーザー進捗の同期要求

禁止事項:

- D88ファイルのコピー
- SQLiteへの直接アクセス
- SDL描画
- プラットフォーム固有HTTP APIの直接呼び出し

### 3.2 `RaHttpClient`

`rc_client_server_call_t`を実装する非同期HTTP抽象層とする。

共通インターフェース:

```cpp
enum class RaHttpPurpose {
    Api,
    Image
};

struct RaHttpRequest {
    uint64_t request_id;
    RaHttpPurpose purpose; // ApiまたはImage
    std::string url;
    std::optional<std::string> post_data;
    std::string content_type;
    uint32_t connect_timeout_ms;
    uint32_t total_timeout_ms;
    size_t max_response_bytes;
};

struct RaHttpResponse {
    uint64_t request_id;
    int transport_result;
    int http_status;
    std::string content_type;
    std::vector<uint8_t> body;
    std::string error;
};

class RaHttpClient {
public:
    virtual void Send(RaHttpRequest request) = 0;
    virtual void Cancel(uint64_t request_id) = 0;
    virtual void CancelAll() = 0;
    virtual void DrainCompleted(std::vector<RaHttpResponse>& output) = 0;
    virtual ~RaHttpClient() = default;
};
```

規則:

- 接続タイムアウト10秒、全体タイムアウト30秒とする。
- レスポンス本文の上限はAPI応答8MiB、画像8MiBとする。
- `rc_api_request_t::post_data == NULL`ならGET、非NULLならPOSTとする。空文字列のPOSTを
  GETへ変換しない。
- RA API要求はredirectを追跡しない。認証情報を別hostへ転送しないためである。
- 画像GETだけHTTPSからHTTPSへのredirectを最大5回許可する。
- TLS証明書検証を無効化する設定は設けない。
- RA API要求にXM8のCookieを独自追加しない。
- User-Agentは`XM8/<version> <rc_client_get_user_agent_clause()> (<platform>)`とする。
- 完了通知はロック付きキューへ積み、メインスレッドの`DrainCompleted()`で処理する。
- `Send()`はrequestをworkerへqueueして即時returnし、main threadやVM lock保持中に
  DNS、socket、file I/Oを実行しない。
- 各requestはterminal flagを持ち、cancel完了と遅延network完了の先着1件だけを採用する。
- `rc_client_server_call_t`へ渡されたURL、post data、content typeはcallbackが戻るまでしか
  有効とは限らないため、`Send()`前に所有bufferへコピーする。
- API transportは成功、失敗、cancelのいずれでも、client破棄前に
  `rc_client_server_callback_t`をちょうど1回呼ぶ。cancelはclient error応答へ変換する。
- ユーザー操作のcancelでは対応する`rc_client_async_handle_t`を
  `rc_client_abort_async()`してからtransportをcancelする。世代番号はcallback自体を省略する
  ためではなく、callback後のXM8状態更新を破棄するために使う。
- shutdownは`CancelAll()`、完了queue drain、全callback終了、worker join、
  `rc_client_destroy()`の順とし、client破棄後にcallbackを呼ばない。
- DNS、接続timeout、一時的なTLS/通信失敗は
  `RC_API_SERVER_RESPONSE_RETRYABLE_CLIENT_ERROR`、恒久的なclient失敗は
  `RC_API_SERVER_RESPONSE_CLIENT_ERROR`へ変換する。
- outbound API dataは`rc_client`が生成した認証、hash、session、unlock、Leaderboard、Ping、
  library sync requestに限定する。D88 bytes、working copy、state、DB、原本pathを追加しない。

プラットフォーム実装:

| OS | 実装 |
|---|---|
| Windows | WinHTTP。非同期コールバックを内部キューへ変換 |
| macOS | Objective-C++アダプタから`NSURLSession`を使用 |
| Linux | libcurl multi APIを専用ワーカースレッドで使用 |
| Android | Java `HttpURLConnection`をExecutorで実行しJNIで完了通知 |

### 3.3 `RaLibrary`

ゲーム、媒体、起動構成、同期済み進捗を管理する。詳細は
[02_ゲームライブラリとD88保存仕様.md](02_ゲームライブラリとD88保存仕様.md)で定義する。

### 3.4 `RaMediaStore`

原本の検証、MD5計算、作業コピー生成、破損検出、再作成だけを担当する。
VMへの挿入は担当しない。

### 3.5 `RaOverlay`

RA画面と通知の状態を保持し、既存`Video`の最終合成直前に描画する。
詳細は[03_オーバーレイUI仕様.md](03_オーバーレイUI仕様.md)で定義する。

### 3.6 `RaImageCache`

画像URLからバッジ、ゲーム画像、アバターを取得し、デコード済みRGBAまたは
プレースホルダーを`RaOverlay`へ返す。HTTPは`RaHttpClient`を共有する。

### 3.7 `RaSessionPolicy`

操作の許可判定を一箇所へ集約する。

```cpp
enum class RaRestrictedAction {
    SaveState,
    LoadState,
    AutoSaveState,
    AutoLoadState,
    FullSpeed,
    ChangeSpeed,
    PseudoFastDisk,
    DebuggerOrMemoryTools,
    Pause,
    Reset,
    ChangeMedia,
    ChangeSystem
};

struct RaActionDecision {
    bool allowed;
    bool requires_reset;
    const char* message_key;
};
```

UIとショートカットは必ず同じ判定APIを通す。メニューだけを無効にして
キーボードショートカットが残る実装は禁止する。

`PseudoFastDisk`は現行実装の`config.ignore_crc`を指す。この設定はD88のCRCエラーを
無視するだけでなくFDC event間隔も短縮するため、オンラインRAセッションでは
Softcore/Hardcoreを問わず禁止する。デバッガ、breakpoint、frame step、メモリ書換えなどの
診断機能も同様に禁止する。現行UIに入口がなくても、将来入口を追加するときは必ず
`RaSessionPolicy`を経由させる。

### 3.8 `RaStateStore`

RA専用state path、RA chunk/footerの保存、VM変更前のpreflight、progress serializeを
担当する。`App::Save()`/`Load()`から既存の設定、DiskManager、TapeManager、VMの直列化を
`SaveStateBody(FILEIO&)`と`LoadStateBody(FILEIO&)`へ抽出し、Normal wrapperとRA wrapperで
共有する。RA loadはpreflight成功後だけ`LoadStateBody()`を呼ぶ。Normal state pathと既存formatを
変更しない。

### 3.9 `RaTextRenderer`

RA由来UTF-8の検証、glyph幅計算、既存KANJI ROMへ描画可能なShift-JISへの安全な変換、
非対応文字の置換を担当する。DB内文字列の所有や画面layoutは担当しない。

## 4. RAセッション状態機械

`RaService`は次の状態だけを持つ。

```text
Disabled
  └─ Enable -> LoggedOut

LoggedOut
  ├─ Login -> Authenticating
  ├─ StartGame -> AwaitingLogin
  └─ Disable -> Disabled

Authenticating
  ├─ Success -> Ready
  └─ Failure -> LoggedOut

AwaitingLogin
  ├─ Submit -> AuthenticatingForLaunch
  ├─ ContinueOffline -> OfflineSession
  └─ CancelLaunch -> LoggedOut

AuthenticatingForLaunch
  ├─ Success -> Identifying
  └─ Failure -> OfflineSession

Ready
  ├─ StartGame -> Identifying
  └─ Logout -> LoggedOut

Identifying
  ├─ Success -> StartingSession
  ├─ Failure -> OfflineSession
  └─ Cancel -> Ready

StartingSession
  ├─ Success -> Active
  ├─ Failure -> OfflineSession
  └─ Cancel -> Ready

Active
  ├─ ChangeMedia -> ChangingMedia
  ├─ ConnectionLoss -> ActiveDisconnected
  └─ StopGame -> Ready

ChangingMedia
  ├─ Success and VM swap -> Active
  ├─ RA failure -> Active（旧媒体を維持）
  ├─ VM swap and RA rollback failure -> OfflineSession
  └─ StopGame -> Ready

ActiveDisconnected
  ├─ Reconnected -> Active
  └─ StopGame -> Ready

OfflineSession
  └─ StopGame -> Ready または LoggedOut
```

- `OfflineSession`から`Active`への遷移は禁止する。
- `ActiveDisconnected`はRA開始済みセッション内の一時切断であり、
  `rc_client`が保持する保留解除の再送を許可する。
- `OfflineSession`の実効ポリシーはNormal相当とし、Hardcore表示とHardcore解除を行わない。
  ただし媒体は引き続きRA作業コピーだけを使う。
- `Identifying`または`StartingSession`中はVMを開始しない。
- 失敗時に`OfflineSession`へ確定してからVMを開始する。
- 遅れて到着した非同期結果はセッション世代番号が一致しなければ破棄する。
- `AwaitingLogin`へ入る前に原本検証と作業コピー生成を完了する。Login画面をcancelしても
  原本を直接開かず、確定済み作業コピーからOffline sessionを開始する。
- RetroAchievementsメニューから明示的に行う通常ログイン失敗は`LoggedOut`へ戻し、ゲーム起動待ちの
  login失敗だけを`OfflineSession`へ遷移させる。

## 5. `rc_client`統合

### 5.1 初期化

- `rc_client_create(ReadMemory, ServerCall)`を1回呼ぶ。
- `rc_client_set_event_handler()`を登録する。
- `rc_client_set_userdata()`に`RaService`を設定する。
- `rc_client`はHardcore既定ONのため、create直後に
  `rc_client_set_hardcore_enabled(client, 0)`を必ず呼ぶ。
- `rc_client_enable_logging()`はリリースではWARN、デバッグではINFOを既定とする。
- ログコールバックで認証パラメータとトークンを必ず伏せる。
- `RC_CLIENT_SUPPORTS_HASH`を有効にしてビルドする。

### 5.2 ログイン

- 初回入力は`rc_client_begin_login_with_password()`を使う。
- 成功時に`rc_client_get_user_info()`からユーザー名とトークンを取得する。
- 再起動後は`rc_client_begin_login_with_token()`を使う。
- パスワードは呼出し完了直後に上書きして破棄し、DBやログへ保存しない。

### 5.3 ゲーム開始

1. `RaMediaStore`が原本の媒体MD5、選択bankのRA識別hash、作業コピーを確定する。
2. 選択モードを`rc_client_set_hardcore_enabled()`へ反映する。Softcoreでは0、
   Hardcoreでは1を明示する。
3. RA識別hashを`rc_client_begin_load_game()`へ渡す。
4. 成功時、`rc_client_get_game_info()`のGame ID、タイトル、ハッシュ、バッジURLをDBへ保存する。
5. RAセッション開始成功後に作業コピーをDriveへ挿入し、VMをcold resetする。
6. VM reset直後に`rc_client_reset()`を1回呼んでから最初のフレームを実行する。
7. 未識別または通信失敗時はRA無効の`OfflineSession`として同じ作業コピーから開始する。

手順7では`rc_client_unload_game()`を呼び、Hardcoreを0へ戻してからVMを開始する。
Offline session中は`rc_client_do_frame()`を呼ばず、停止ループの認証・UI用に必要な
`rc_client_idle()`だけを呼ぶ。

`rc_client_begin_identify_and_load_game()`へD88バッファを渡す方式は使用しない。
XM8側で公式と同じRA識別hashを計算済みであり、D88全体を追加保持する必要がないためである。

DB、原本読出し、D88検証、作業コピー生成に失敗した場合は手順3へ進まない。
原本を直接VMへ渡すfallbackを提示せず、RAモード起動を中止する。ユーザーが明示的に
Normalで開き直す操作だけを別途提供する。

既存`App::OpenDiskFromUser()`をfile menu、CLI、drag-and-drop、M3Uの共通入口として維持し、
RA有効時は直接`DiskManager::Open()`へ進まず、登録・copy・識別を行うlaunch coordinatorへ
委譲する。後続Driveの単純挿入も`RaSessionPolicy`を通し、入口ごとの迂回を作らない。

### 5.4 ライブラリ同期

ログイン成功後、ゲーム未実行時に次を順番に実行する。

1. `rc_client_begin_fetch_hash_library(RC_CONSOLE_PC8800)`でhashとGame IDの対応を取得する。
2. ローカル媒体MD5およびbank別RA識別hashと照合し、媒体/bank単位のRA Game IDと
   識別状態を更新する。
3. 新規Game IDをまとめて`rc_client_begin_fetch_game_titles()`へ渡し、titleとbadge URLを更新する。
4. `rc_client_begin_fetch_all_user_progress(RC_CONSOLE_PC8800)`でユーザー別解除数を更新する。

- 同期結果は1トランザクションずつ適用し、途中失敗時は前回成功値を維持する。
- 同期はゲーム開始を必須にはしないが、実行中は自動開始せず次回idle時へ延期する。
- 全進捗APIで得られないポイント値はNULLのまま保持し、ゲームload時のsummaryで更新する。
- ライブラリ同期結果だけでゲームセッション開始済みとはみなさない。起動時は常に
  `rc_client_begin_load_game()`を呼ぶ。

### 5.5 媒体変更

- RA active mediaは起動構成の`is_ra_anchor=1`で示す1媒体だけとする。
- 補助ドライブの通常挿入ではRA active mediaを変更しない。
- ライブラリの「ディスク交換」操作だけが
  `rc_client_begin_change_media()`を呼ぶ。
- APIへ渡すhashは対象bankの登録時RA識別hashであり、ゲーム書込み後の`working.d88`を
  再hashしない。
- 変更先ハッシュが同じRAゲームに属さない場合、挿入を中止して元の媒体を維持する。
- API呼出し前に変更先作業コピーをD88 probeし、対象Driveへ挿入可能であることを確認する。
- RA変更成功後にVMのディスクを交換する。VM交換が予期せず失敗した場合は旧hashへ
  `rc_client_begin_change_media()`してrollbackする。
- rollbackにも失敗した場合はRAセッションを終了して`OfflineSession`へ移し、VMには
  交換前媒体を維持する。RA active mediaとVM媒体が不一致のまま評価を続けない。

## 6. PC-88メモリ公開

RA公開アドレスを次へ固定する。

| RAアドレス | 長さ | XM8実体 |
|---|---:|---|
| `0x00000-0x0FFFF` | 65536 | `PC88::ram` |
| `0x10000-0x10FFF` | 4096 | `PC88::tvram` |

- CPUの現在のバンクマップではなく物理配列を読む。
- GVRAM、拡張RAM、ROM、I/Oは初期対応では公開しない。
- 範囲外または境界をまたぐ要求は、読み取れる先頭部分だけを返す。
- 先頭アドレスが完全に範囲外なら0バイトを返す。

VM公開API:

```cpp
uint32_t VM::read_retroachievements_memory(
    uint32_t address,
    uint8_t* buffer,
    uint32_t num_bytes) const;
```

`PC88`には同じ契約のメソッドを追加し、`VM`はそれを転送する。
読み出し中にwait、I/O、メモリマッパ、デバイス状態を変更してはならない。

## 7. フレームとスレッド

### 7.1 実フレーム完了点

現行XM8の`EVENT::create_sound32()`は音声bufferを満たすため、1回のAppループ内で
`EVENT::drive()`を複数回呼び得る。したがって`create_sound32()`の後で
`rc_client_do_frame()`を1回だけ呼ぶ実装は禁止する。

- `EVENT::drive()`の1フレーム処理とsound mixが完了した直後に、汎用の
  `EMU::on_frame_completed()` host callbackを1回呼ぶ。
- callbackは`EMU_SDL`を介してAppのRA frame sinkへ転送する。RA無効buildでは
  compile時no-opとし、EVENTへRA型を持ち込まない。
- frame sink内では`rc_client_do_frame()`とRAイベントのdeep copyだけを行う。
  SDL描画、DB更新、HTTP完了処理を行わない。
- full speed、描画skip、1回の音声生成で複数frameが進む場合も、完了した全frameを評価する。

Appループでは入力処理後にHTTP・画像・RAイベントqueueを取り込み、VM実行後の描画で
通知とオーバーレイを合成する。メニュー、一時停止、バックグラウンドでVMを実行しない
ループでは`rc_client_idle()`を呼ぶ。現行の無期限`SDL_WaitEvent()`をRA active時だけ
最大1秒timeoutへ変更し、background中もmain threadでidleを継続する。

### 7.2 スレッド制約

- `rc_client_do_frame()`、`rc_client_idle()`、メモリコールバック、イベントハンドラ、
  UI更新はメインスレッドだけで実行する。
- `rc_client_event_t`とその参照先はevent callback中だけ有効とみなし、表示に必要な文字列、
  ID、scoreboard entriesを所有型へdeep copyして最大256件のqueueへ積む。tracker/progressの
  同一ID更新は最新値へcoalesceし、解除・完了・server errorを低優先更新より先に保持する。
- frame callbackはVM lock保持中に呼ばれるため、イベントhandlerからVideo、DB、
  DiskManagerを再入しない。
- HTTPとファイル走査はワーカースレッドで実行できる。
- SQLite接続は`RaLibrary`所有スレッドに限定する。初期実装ではメインスレッド所有とする。
- ワーカーからDBへ直接書かず、結果オブジェクトをメインスレッドへ返す。
- アプリ終了時は非同期要求をキャンセルし、ワーカーをjoinしてから
  `rc_client_destroy()`を呼ぶ。

## 8. エラー分類

```cpp
enum class RaErrorDomain {
    None,
    Authentication,
    Transport,
    Tls,
    Http,
    Server,
    GameIdentification,
    Media,
    Database,
    Image,
    Internal
};
```

エラーにはdomain、安定したcode、ユーザー表示用message key、診断文字列を持たせる。
診断文字列はトークン、パスワード、POST本文、原本の絶対パスを含めない。

ゲーム開始前の認証・識別・セッションエラーは`OfflineSession`へ遷移する。
ゲーム開始後の一時的な通信エラーは`rc_client`の切断イベントに従い、
ただちにRAを無効化しない。

媒体、DB、作業コピーのエラーはローカル整合性エラーであり、原本を直接開いて
継続しない。RAモード起動を中止し、Normalで開き直す明示操作だけを提示する。
