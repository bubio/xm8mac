# ゲームライブラリとD88保存仕様

## 1. 目的

RAのゲーム識別はD88の内容に対するMD5で行われる。一方、PC-88ゲームには
マルチイメージD88、複数D88、2ドライブ同時利用が存在する。本仕様では、
RAの識別単位である「媒体」と、ユーザーが認識する「ゲーム」を分離する。

## 2. 保存場所

既存`Setting::GetSettingDir()`が返すアプリ設定ディレクトリ配下に`ra/`を作る。

```text
ra/
  library.sqlite3
  library.sqlite3-wal
  library.sqlite3-shm
  credentials_user.txt
  states/
    <ra_game_id>/<anchor_md5>/
    offline/<anchor_md5>/
  media/
    <32文字MD5>/
      working.d88
  images/
    game/
    achievement/
    user/
  temp/
```

- パス結合は専用ヘルパーを使い、文字列`strcat`を新規コードで使用しない。
- `ra/temp/`は起動時に走査する。`.trash`/`.old`は対応するmedia行とworking fileの
  有無からrestoreまたは削除を決定し、単純な経過時間だけで削除しない。登録途中の
  `.part`だけは24時間以上前なら削除する。
- `media/<md5>/`のディレクトリ名は小文字ASCIIのMD5だけを許可する。
- Androidでも保存先はアプリ専用ストレージとし、SAFツリーへ作業コピーを置かない。
- Android Auto Backup/Data Extraction Rulesから`ra/`全体を除外し、credentials、原本locator、
  working D88、RA stateをクラウドへ送らない。

## 3. 識別モデル

### 3.1 ゲーム

DB上の内部起動単位。1つ以上の媒体と1つの標準起動構成を持つ。
RA modeで元ファイルを保護するため、RA未識別媒体も内部行として保持できる。
ユーザー向けRetroAchievements Libraryに表示する「ゲーム」は、`ra_game_id`を持ち
`identification_state=1`のRA識別済み行だけとする。

### 3.2 媒体

1つのD88ファイル全体。主キーはファイル全体MD5である。同一内容のD88はファイル名や
保存場所が異なっても同じ媒体として扱う。これは作業コピーと保存データ管理用のIDであり、
RAサーバーへ渡すゲーム識別hashとは分離する。

### 3.3 bank

D88内部のイメージ番号。bankは媒体の子要素である。マルチイメージD88では、
起動時に選択したbankのD88イメージ範囲からRA識別hashを計算する。
bank切替だけでRA active mediaは自動変更しないが、RAのディスク交換操作では
交換先bankのRA識別hashを使う。

### 3.4 起動構成

Drive 1/2へ割り当てる媒体とbankを示す。RA識別基準媒体は必ず1つとし、
通常はDrive 1の媒体を使うが、DB上で明示的に保持する。

## 4. SQLite仕様

### 4.1 接続設定

DBを開いた直後に次を実行する。

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA busy_timeout = 3000;
```

- DBファイルはアプリの単一プロセスだけが書き込む。
- すべてのスキーマ変更は`BEGIN IMMEDIATE`トランザクション内で行う。
- `PRAGMA user_version`ではなく`schema_meta`を正とする。
- SQL文字列へ値を連結せず、必ずprepared statementを使用する。

文字列はUTF-8を検証してからDBへ保存する。ICUは同梱しないため、`sort_title`と検索keyは
ASCII `A-Z`だけを小文字化し、非ASCII code pointは正規化せず保持する。検索はASCIIでは
大文字小文字を区別せず、日本語などcaseを持たない文字はUTF-8部分一致とする。

### 4.2 初期スキーマ

```sql
CREATE TABLE schema_meta (
    singleton INTEGER PRIMARY KEY CHECK(singleton = 1),
    schema_version INTEGER NOT NULL,
    created_at INTEGER NOT NULL,
    migrated_at INTEGER NOT NULL
);

CREATE TABLE ra_settings (
    singleton INTEGER PRIMARY KEY CHECK(singleton = 1),
    enabled INTEGER NOT NULL DEFAULT 0 CHECK(enabled IN (0, 1)),
    last_mode INTEGER NOT NULL DEFAULT 1 CHECK(last_mode IN (1, 2)),
    unofficial_enabled INTEGER NOT NULL DEFAULT 0 CHECK(unofficial_enabled IN (0, 1)),
    encore_enabled INTEGER NOT NULL DEFAULT 0 CHECK(encore_enabled IN (0, 1)),
    spectator_enabled INTEGER NOT NULL DEFAULT 0 CHECK(spectator_enabled IN (0, 1)),
    notification_seconds INTEGER NOT NULL DEFAULT 5 CHECK(notification_seconds IN (3, 5, 8)),
    image_cache_limit_mib INTEGER NOT NULL DEFAULT 128 CHECK(image_cache_limit_mib IN (64, 128, 256)),
    updated_at INTEGER NOT NULL
);

CREATE TABLE games (
    id INTEGER PRIMARY KEY,
    ra_game_id INTEGER UNIQUE,
    title TEXT NOT NULL,
    sort_title TEXT NOT NULL,
    title_source INTEGER NOT NULL DEFAULT 0,
    badge_url TEXT,
    rich_presence TEXT,
    identification_state INTEGER NOT NULL DEFAULT 0,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    last_played_at INTEGER,
    CHECK(ra_game_id IS NULL OR ra_game_id > 0),
    CHECK(title_source IN (0, 1, 2)),
    CHECK(identification_state BETWEEN 0 AND 4)
);

CREATE TABLE media (
    md5 TEXT PRIMARY KEY,
    game_id INTEGER REFERENCES games(id) ON DELETE SET NULL,
    ra_game_id INTEGER,
    identification_state INTEGER NOT NULL DEFAULT 0,
    source_kind INTEGER NOT NULL,
    source_locator TEXT NOT NULL,
    source_display_name TEXT NOT NULL,
    source_size INTEGER NOT NULL,
    source_mtime INTEGER,
    bank_count INTEGER NOT NULL,
    working_relpath TEXT NOT NULL,
    ordinal INTEGER,
    health_state INTEGER NOT NULL DEFAULT 0,
    detached_at INTEGER,
    created_at INTEGER NOT NULL,
    verified_at INTEGER NOT NULL,
    CHECK(length(md5) = 32),
    CHECK(md5 NOT GLOB '*[^0-9a-f]*'),
    CHECK(ra_game_id IS NULL OR ra_game_id > 0),
    CHECK(identification_state BETWEEN 0 AND 4),
    CHECK(source_kind IN (0, 1)),
    CHECK(source_size > 0 AND source_size <= 1073741824),
    CHECK(bank_count > 0),
    CHECK(ordinal IS NULL OR ordinal >= 0),
    CHECK(health_state BETWEEN 0 AND 4),
    CHECK((game_id IS NULL AND ordinal IS NULL AND detached_at IS NOT NULL) OR
          (game_id IS NOT NULL AND ordinal IS NOT NULL AND detached_at IS NULL)),
    UNIQUE(game_id, ordinal),
    UNIQUE(game_id, md5)
);

CREATE TABLE media_banks (
    media_md5 TEXT NOT NULL REFERENCES media(md5) ON DELETE CASCADE,
    bank_index INTEGER NOT NULL,
    label TEXT NOT NULL,
    ra_hash TEXT,
    ra_game_id INTEGER,
    identification_state INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY(media_md5, bank_index),
    CHECK(bank_index >= 0),
    CHECK(ra_hash IS NULL OR (length(ra_hash) = 32 AND
          ra_hash NOT GLOB '*[^0-9a-f]*')),
    CHECK(ra_game_id IS NULL OR ra_game_id > 0),
    CHECK(identification_state BETWEEN 0 AND 4)
);

CREATE TABLE launch_profiles (
    game_id INTEGER NOT NULL REFERENCES games(id) ON DELETE CASCADE,
    drive INTEGER NOT NULL,
    media_md5 TEXT NOT NULL REFERENCES media(md5),
    bank_index INTEGER NOT NULL,
    is_ra_anchor INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY(game_id, drive),
    CHECK(drive IN (0, 1)),
    CHECK(is_ra_anchor IN (0, 1)),
    FOREIGN KEY(game_id, media_md5) REFERENCES media(game_id, md5),
    FOREIGN KEY(media_md5, bank_index) REFERENCES media_banks(media_md5, bank_index)
);

CREATE UNIQUE INDEX one_ra_anchor_per_game
ON launch_profiles(game_id)
WHERE is_ra_anchor = 1;

CREATE TABLE progress (
    username TEXT NOT NULL,
    ra_game_id INTEGER NOT NULL,
    core_total INTEGER NOT NULL,
    core_unlocked INTEGER NOT NULL,
    hardcore_unlocked INTEGER NOT NULL,
    points_total INTEGER,
    points_unlocked INTEGER,
    synced_at INTEGER NOT NULL,
    PRIMARY KEY(username, ra_game_id),
    CHECK(ra_game_id > 0),
    CHECK(core_total >= 0),
    CHECK(core_unlocked BETWEEN 0 AND core_total),
    CHECK(hardcore_unlocked BETWEEN 0 AND core_total),
    CHECK(points_total IS NULL OR points_total >= 0),
    CHECK(points_unlocked IS NULL OR points_unlocked >= 0)
);

CREATE TABLE image_cache (
    id INTEGER PRIMARY KEY,
    url TEXT NOT NULL UNIQUE,
    image_kind INTEGER NOT NULL,
    relative_path TEXT NOT NULL UNIQUE,
    content_type TEXT NOT NULL,
    byte_size INTEGER NOT NULL,
    last_used_at INTEGER NOT NULL,
    etag TEXT,
    modified TEXT,
    CHECK(image_kind BETWEEN 0 AND 3),
    CHECK(byte_size > 0)
);

CREATE TABLE sync_state (
    sync_key TEXT PRIMARY KEY,
    completed_at INTEGER NOT NULL,
    result_code INTEGER NOT NULL
);

CREATE INDEX games_sort_title ON games(sort_title);
CREATE INDEX games_last_played ON games(last_played_at DESC);
CREATE INDEX media_game_order ON media(game_id, ordinal);
```

列挙値:

| 列 | 値 |
|---|---|
| `games.identification_state` | 0=未照合、1=RA対応、2=RA未登録、3=照合エラー、4=媒体競合 |
| `media.identification_state` | 0=未照合、1=RA対応、2=RA未登録、3=照合エラー、4=所属ゲームと不一致 |
| `media_banks.identification_state` | 0=未照合、1=RA対応、2=RA未登録、3=照合エラー、4=所属ゲームと不一致 |
| `title_source` | 0=D88/ファイル名、1=RA、2=ユーザー編集 |
| `source_kind` | 0=デスクトップパス、1=Android SAF URI |
| `health_state` | 0=正常、1=原本不明、2=原本変更、3=作業コピー不明、4=作業コピー破損 |
| `image_kind` | 0=ゲーム、1=実績、2=ユーザー、3=Subset |

### 4.3 スキーマ更新

- 初期実装の`schema_version`は1、bank別RA同期追加後は2とする。
- v1からv2では`media_banks`へ`ra_hash`、`ra_game_id`、`identification_state`を追加する。
  単一bank媒体は`media.md5`を`ra_hash`へ移行し、既存マルチbank媒体は次回probe時に
  bank別hashを補完する。
- `schema_meta`と`ra_settings`は`singleton=1`の1行だけを持つ。
- 各更新は`MigrateFromNToNPlus1()`の連続処理として実装する。
- 未知の新しいスキーマを開いた場合は書き込みせず、RA機能を無効化する。
- `SQLITE_CORRUPT`またはintegrity check失敗時は接続を閉じ、DB、`-wal`、`-shm`を
  同じUTC timestampの隔離名へ移す。sidecarを元の名前に残したまま新規DBを作らない。
- 3ファイルの隔離に失敗した場合は元DBをread-onlyで保持し、RA機能を無効化する。
- 破損DBから自動で部分データを取り出さない。媒体ファイルは削除しない。

## 5. D88検証とMD5

### 5.1 対象データ

- 保存管理用の媒体MD5対象はD88の先頭バイトからファイル末尾までである。
- RA識別hash対象は起動に使うD88イメージ1枚分である。単一イメージD88では
  ファイル全体、マルチイメージD88では選択中bankの`image_size`範囲だけを対象にする。
- ヘッダ正規化、ライトプロテクト変更、ファイル名追加を行わない。
- アルゴリズムは`rcheevos`の`RC_CONSOLE_PC8800`と同じMD5とする。
- M3U自体の内容は媒体ハッシュへ含めない。
- D88サイズ上限は1GiBとし、全体をメモリへ保持せず64KiB単位で処理する。

### 5.2 検証順序

1. 入力を読み取り専用で開く。
2. ファイルサイズを取得し、0バイトと実装上の最大値超過を拒否する。
3. 既存`ProbeD88Image()`と同じ受理結果・bank数を返す副作用なしparserで構造を確認する。
4. 先頭から末尾まで読みながらMD5を計算する。
5. 読み取り完了時のサイズが開始時と一致することを確認する。
6. デスクトップでは可能ならmtimeも再取得し、途中変更を検出する。
7. 変更を検出した場合は登録せず、再試行を要求する。

D88解析とMD5計算は同じストリーム走査へ統合してよいが、解析失敗時に
不完全なDB行や作業コピーを残してはならない。

parserは各bank sizeがヘッダ以上で加算がoverflowせず、少なくとも1 bankが完全に
読めることを確認する。最後に解釈したbankより後ろにpaddingまたは未解釈suffixがあっても、
現行`ProbeD88Image()`が成功する入力は拒否せず警告状態として記録し、MD5には末尾まで
含める。RAモードだけ既存D88互換性を狭めてはならない。

## 6. 作業コピー生成

### 6.1 新規登録

作業コピー生成は次の順序で行う。

1. `ra/temp/<random>.d88.part`を排他的に作成する。
2. 原本を64KiB単位で読み、MD5計算と一時ファイルへの書き込みを行う。
3. 一時ファイルをflushし、OSが提供する場合はfsync相当を実行する。
4. 一時ファイルを再度読み、MD5とD88構造を検証する。
5. `ra/media/<md5>/`を作成する。
6. 一時ファイルを`working.d88`へ同一ファイルシステム上でatomic renameする。
7. DBトランザクションでゲーム、媒体、bank、起動構成を登録する。
8. DB commit後に成功をUIへ通知する。

手順6後にDB commitが失敗した場合は、配置済みファイルを削除する。
削除に失敗しても次回起動時の孤立媒体監査で回収できるようログへ記録する。

### 6.2 既存MD5

- DB行と正常な`working.d88`が存在すれば再利用する。
- `game_id IS NULL`の分離済み媒体なら、新しいゲームへ再接続して`detached_at`をNULLにする。
- DB行がありファイルがない場合は原本から再作成する。
- DB行がなく同名ディレクトリだけある場合は、そのファイルを信用せずMD5検証する。
- 既存作業コピーのMD5が主キーと異なる場合、ユーザーのゲーム内セーブを含むため
  破損とはみなさない。D88への正常なゲーム書き込みでもMD5は変化する。

重要: 作業コピーの現在MD5を原本MD5と比較してはいけない。作成直後だけ一致を確認し、
以後はD88構造とファイルの存在・読込可能性で健全性を判定する。

ライブラリからの起動時は次の規則を使う。

- 作業コピーが存在してprobe可能なら、原本が消失していても登録済みMD5で起動できる。
- 原本のsize/mtimeが登録値と同じなら毎回MD5を再計算しない。
- size/mtimeが変化した場合は原本を再hashする。同じMD5ならmetadataだけ更新する。
- 異なるMD5なら既存作業コピーを上書きせず、「既存セーブから起動」または
  「変更後原本を新しい媒体として登録」を選択させる。自動でセーブを移行しない。
- Android SAFでmtimeが得られない場合はsize変化時とユーザーの原本再検証操作時に再hashする。

### 6.3 セーブデータ初期化

1. ゲームを実行中なら操作を拒否する。
2. 確認オーバーレイでゲーム名、媒体名、失われる内容を表示する。
3. 原本を再検証し、登録時MD5と一致することを確認する。
4. 新しい一時コピーを作成・検証する。
5. 既存`working.d88`を`ra/temp/<md5>-<operation-id>.old`へrenameする。
6. 新コピーを`working.d88`へrenameする。
7. 成功後に`.old`を削除する。失敗時は`.old`を戻す。crash後はworking fileがなければ
   `.old`を復元し、working fileが正常なら`.old`を削除する。

## 7. ゲーム登録

### 7.1 単体D88

- 登録時はD88ヘッダのbank 0名称、または拡張子を除いたファイル名を内部暫定名に使う。
- 内部暫定名は作業コピーと起動構成を管理するための診断値であり、
  ユーザー向けRetroAchievements Libraryの主表示には使わない。
- RA照合成功後はRA Game ID、RAタイトル、badge URLを保存し、Library表示対象へ昇格する。
- ユーザーが手動変更したタイトルは`title_source=2`とし、RA同期で上書きしない。
- RA modeでは未識別でも作業コピーを使い、元ファイルへライトバックしない。

### 7.2 M3U

- UTF-8 BOMを許可し、空行と`#`コメントを無視する。
- 相対パスはM3Uの親ディレクトリ基準で解決する。
- 既存`LoadM3U()`の解析結果を共通利用する。
- 全エントリを登録し、記載順を`ordinal`とする。
- ゲーム識別とRA anchorには先頭の正常なD88を使う。
- 先頭エントリが失敗した場合に後続へ自動フォールバックしない。M3Uをエラーとする。
- M3UはDrive割当を表現しないため、標準起動構成は先頭媒体をDrive 1へ割り当て、
  Drive 2は未割当とする。2ドライブ同時使用はユーザーが媒体構成画面で明示する。

### 7.3 フォルダ走査

- 拡張子`.d88`、`.D88`、`.m3u`、`.M3U`を対象とする。
- シンボリックリンクのディレクトリを再帰追跡しない。
- 1回の取り込み上限は10,000候補とし、超過時は中止して通知する。
- M3Uに含まれるD88を先に登録し、その後の単体走査ではMD5重複として再利用する。
- ファイル名の`Disk A`、`Disk B`等を根拠に自動グループ化しない。
- 走査はワーカースレッド、DB反映はメインスレッドで小分けに行い、進捗と取消を提供する。

## 8. RAライブラリ同期

ログイン後、ゲームを実行していない状態で次を行う。

1. `rc_client_begin_fetch_hash_library(RC_CONSOLE_PC8800)`の結果を一時mapへ保持する。
2. `media.md5`ごとにRA Game IDと識別状態を更新する。
3. `games`のanchor媒体と同じGame IDをゲームの`ra_game_id`にする。
4. Game IDを重複除去して最大100件ずつ`rc_client_begin_fetch_game_titles()`へ渡す。
5. `rc_client_begin_fetch_all_user_progress(RC_CONSOLE_PC8800)`を取得し、`progress`を更新する。
6. 全工程成功時だけ`sync_state`の完了時刻を更新する。

- hash libraryに存在しないMD5はRA未登録とする。通信失敗と混同しない。
- RA未登録、未照合、照合エラーの内部行はユーザー向けLibrary v1には表示しない。
- ゲームload成功時も同じくRA Game ID、RAタイトル、badge URLを保存し、
  以後LibraryではRAタイトルを表示する。
- M3Uまたは手動指定で同じゲームに属する媒体が異なるRA Game IDへ解決された場合、
  グループを自動分割せず媒体競合として表示する。
- 競合媒体は補助Driveへ挿入できるが、RA anchorまたはRAディスク交換先に指定できない。
- 同じRA Game IDの別ローカルゲームは即時統合せず媒体競合として表示する。
  利用者がGame Detailの`MERGE`を明示実行した場合だけ、1トランザクションで
  媒体移動、起動構成整理、旧ゲーム削除を行う。
- all progress応答にポイントが含まれない場合、`points_total`と`points_unlocked`はNULLを
  維持し、ゲームload時の`rc_client_get_user_game_summary()`で得られる値だけを保存する。

## 9. 複数媒体のグループ化

所属決定の優先順位を固定する。

1. 同じM3Uに記載された媒体
2. RA照合で同じRA Game IDになった媒体
3. ユーザーの明示的な「このゲームへ追加」操作
4. 上記以外は別ゲーム

RA照合で別々のローカルゲームが同じGame IDになった場合、まず競合として保存し、
Game Detailの`MERGE`を利用者が明示実行したときだけ次を行う。

- ゲーム実行中は操作を拒否し、停止後に古い`games.id`へ統合する。
- 媒体ordinalは既存媒体の後ろへ追加する。
- 同じMD5は1件にする。
- 起動構成は最初に登録されたゲームを維持する。
- 統合内容を通知し、元へ戻す自動機能は提供しない。

同一ローカルゲーム内の物理媒体が別々のRA Game IDへ解決した場合は、各D88が
単一RA Game IDへ一意に対応するときだけ`SPLIT`を提示する。元のRA anchorを含む媒体は
元ゲームへ残し、ほかをRA Game ID単位の新ゲームへ移動する。1つのマルチbank D88自体が
複数IDへ対応する場合、または他ゲームとの複合競合は`MANUAL`とし自動解消しない。

手動で媒体を別ゲームへ移す場合、移動先に同じMD5があれば操作を拒否する。

M3Uまたはユーザー指定はローカル所属を決める情報であり、RA Game IDの不一致を
上書きしない。媒体ごとの照合結果は保持し、競合をUIへ明示する。

## 10. 起動構成とディスク交換

- Drive番号は内部では0、1、UIではDrive 1、Drive 2と表示する。
- 各Driveへ媒体1つとbank 1つを割り当てる。
- `bank_index`は`media_banks`に存在しなければならない。
- RA anchorは1ゲームに必ず1つ、通常はDrive 1とする。
- RA anchorが起動構成から削除される操作は、新しいanchor指定まで確定させない。
- partial UNIQUE indexはanchorが2件になることだけを防ぐ。0件を防ぐため、
  `RaLibrary::SaveLaunchProfile()`は対象ゲームの2行を1トランザクションで置換し、
  commit前にanchor件数が1であることを検証する。
- `media.game_id`と`launch_profiles.game_id`の複合外部キーにより、別ゲーム媒体を
  起動構成へ直接参照させない。

「bank切替」と「ディスク交換」を区別する。

- 同一D88内のbank切替: RA media変更APIを呼ばない。
- 同一ゲームの別D88へ交換: 媒体のRA Game ID一致とD88 probeを確認し、
  RA変更API成功後にVMへ挿入する。VM挿入失敗時はRA mediaをrollbackする。
- 補助Driveの媒体変更: RA media変更APIを呼ばない。
- 別ゲーム所属媒体の挿入: RAセッション終了とゲーム再起動を要求する。

## 11. ライブラリからの削除

- 「作業コピーを保持」を選択した場合、1トランザクション内で起動構成を削除してから、
  媒体の`game_id`と`ordinal`をNULL、`detached_at`を現在時刻へ更新し、最後にゲームを
  削除する。DB行、bank情報、作業コピーは保持する。
- 同じMD5を再登録した場合、分離済み媒体を再接続し、ゲーム内セーブを復元する。
- 「作業コピーも削除」を選択した場合、実行中でないことを確認し、作業コピーを
  `ra/temp/`のtrash名へrenameしてからDB行を削除する。commit後にtrashを削除し、
  rollback時は元へ戻す。
- trash名にはMD5とoperation IDを含める。起動時にmedia行が残りworking fileがない場合は
  trashを元へ戻し、media行がない場合だけtrashを削除する。
- 起動時の孤立媒体監査は`media`行が存在しないディレクトリだけを対象とし、
  `game_id IS NULL`の分離済み媒体を削除しない。
- 分離済み媒体を一覧・削除する「保存データ管理」をRA設定画面から開けるようにする。

## 12. Android SAF

- SAFから得た`content://` URIを`source_locator`へ保存する。
- `takePersistableUriPermission()`で読取権限を保持する。
- URIの文字列をネイティブの通常パスとして扱わない。
- Java側に`open/read/close/stat/listChildren`のJNIアダプタを追加する。
- フォルダ取り込みは`DocumentFile`で列挙し、ファイル内容をストリームでnative側へ渡す。
- 実行時はアプリ領域の`working.d88`だけを既存`FILEIO`へ渡す。
- URI権限が失効しても既存作業コピーから起動できる。再作成と原本検証だけを無効にする。

## 13. 認証情報保存

RA tokenは`RetroAchivementsIntegrationHandbook/docs/credential-storage.md`に従い、
OSのcredential storeへ保存する。passwordは保存しない。`credentials.bin`形式と
平文token file fallbackは廃止する。

- serviceは`net.retropc.pi.XM8.RetroAchievements`とする。
- accountはRetroAchievements username、secretはRA tokenとする。
- usernameは保存済みtoken loginのaccount hintとして通常ファイルへ保存してよい。
  このファイルにtoken、password、POST body、認証付きURLを含めない。
- macOSはKeychain generic passwordを使う。
- WindowsはCredential ManagerのGeneric Credentialを使い、targetは`<service>:<username>`とする。
- Linux/Raspberry PiはSecret Service/libsecretを使う。利用できない環境ではtokenを保存せず、
  次回起動時にpassword loginを要求する。
- AndroidはAPI 23以上だけRetroAchievementsを有効化し、Android Keystoreでtokenを保護する。
  API 23未満ではRetroAchievements自体を無効にする。
- AndroidではRA関連のapp-private dataをbackup/device-transfer対象から除外する。
- ログアウト時はcredential storeからtokenを削除し、メモリ上のtokenバッファを上書きする。
- 保存token loginが資格情報拒否になった場合は同じtokenを自動再試行せず、credential storeから
  tokenを削除してpassword loginを要求する。

## 14. 画像キャッシュ

- ファイル名は`image_cache.id`と検証済みContent-Typeから`<id>.png`または`<id>.jpg`とし、
  URL由来のパス要素を直接使わない。
- Content-Typeは`image/png`と`image/jpeg`だけを許可する。
- デコード後の最大寸法は2048x2048、最大ピクセル数は4,194,304とする。
- キャッシュ上限は初期値128MiBとし、設定で64/128/256MiBを選択可能にする。
- 上限超過時は`last_used_at`の古い順に、現在表示中でない画像を削除する。
- HTTP失敗、破損画像、未取得中は種類別プレースホルダーを表示する。
