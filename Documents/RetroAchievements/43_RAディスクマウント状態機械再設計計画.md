# RAディスクマウント状態機械 再設計計画・実施結果

基準日: 2026-08-29
実施日: 2026-08-29
仕様明確化: 2026-08-30
状態: 状態遷移表に基づく再実装・自動試験完了

## 1. 目的

RA active mediaはDrive 1の`is_ra_anchor=1`媒体だけとする既存仕様へ実装を戻す。
ディスクのローカル検査・マウントとRAサーバー上のゲーム識別・媒体変更を分離し、
Drive 2を理由に通常のディスク操作を拒否しない。

本文書では、次の3操作を区別する。

1. **ローカル媒体登録・検査**: D88の形式、bank範囲、hashを確認し、
   RAライブラリと作業コピーに登録する。Drive 1、2の両方に必要とする。
2. **Hardcore媒体検証**: 媒体hashが現在のRA Game IDに属するか確認する。
   Drive 2にも必要だが、RA active mediaは変更しない。
3. **RA active media変更**: `rc_client_begin_change_media()`でrcheevosの現在hashを
   変更する。Drive 1 anchorを別D88へ交換する場合だけ実行する。

「Drive 2を検証する」ことと「Drive 2をRA active mediaにする」ことは
同義ではない。

## 2. 判定マトリクス

| 状態 | Drive 1 | Drive 2 |
|---|---|---|
| RA OFF | Normalのまま直接マウント | Normalのまま直接マウント |
| RA ON、未ログイン／ログイン失敗 | 作業コピーをOffline sessionでマウント | ライブラリ登録・ローカル検査後にマウント |
| RA ON、識別中 | 識別完了までVMを開始しない | 登録済み補助媒体として保持し、Hardcoreでは識別後に検証 |
| RA ON、RA未登録 | Offline sessionでマウント | ライブラリ登録・ローカル検査後にマウント |
| RA Casual Active | anchor変更だけをRA媒体変更として扱う | 同一ライブラリgameの登録媒体をマウントし、active hashを変えない |
| RA Hardcore Active | anchor変更だけをRA媒体変更として扱う | 現在のRA Game IDに属するhashと検証後にマウントし、active hashを変えない |

Drive 1 anchorの識別条件はCasualとHardcoreで変えない。HardcoreではDrive 2の
hash所属検証を追加する。またHardcoreではStarting／Active中の
Full Speedを禁止し、Starting中はVMを開始しない。識別失敗後のOffline sessionは
Normal相当とする。

### 2.1 RA検証対象の規範

- RA active mediaの識別を所有するのはDrive 1だけとする。
- Drive 2もRAライブラリの媒体として登録し、hash、所属game、作業コピー、
  bank、起動プロファイルのDrive 2割当を保存する。
- HardcoreでDrive 2をマウントする前に、保存済み検証結果またはRA hash解決で
  現在ロード中のRA Game IDと一致することを確認する。未登録、別Game ID、
  hash解決失敗の媒体はHardcoreのDrive 2へマウントしない。
- Drive 2検証に`rc_client_begin_change_media()`を使わない。検証成功後も
  Drive 1のactive hash、RA session、実績評価対象は変更しない。
- CasualとOffline sessionではHardcore専用のネットワーク検証を待たない。
  ただしRAライブラリ登録、D88ローカル検査、作業コピー使用は省略しない。
- 同一D88内のbank切替は、Drive 1であってもローカルな媒体操作とする。
  bankごとのhashが異なってもRA媒体変更とは判定せず、active hashを変えない。
- `Open Both`でDrive 2のマウントが遅延する場合は、Drive 1 anchorの
  識別、HardcoreでのDrive 2 hash検証、二ドライブのatomic commitを待つためである。

不要なのは、Drive 2検証のためにRA active mediaを切り替えること、
同一検証済みhashを毎回ネットワーク照合すること、Casual／Offlineの
マウントをHardcore用承認待ちで妨げることである。

### 2.2 ライブラリ起動時のDrive 2

- ライブラリはDrive 1だけでなく、そのゲームに所属するDrive 2媒体も
  `media`、`media_banks`、`launch_profiles`に保存する。
- 起動プロファイルにDrive 2割当がある場合は、登録済み作業コピーとbankを
  復元する。割当がない場合はDrive 2を閉じる。
- 起動前に両DriveのD88健全性、所属するローカルgame、bank範囲、作業コピーを
  確認する。HardcoreではさらにDrive 2 hashがDrive 1と同じRA Game IDに属することを
  確認し、すべて成功した後に両Driveをマウントしてcold resetする。
- RAセッションを開始するhashはDrive 1 anchorのみとする。Drive 2 hashは
  Hardcore検証と起動構成復元に使うが、active hashにしない。
- Library起動は選択ゲームの保存済み`launch_profiles`だけを入力とする。起動前に
  現在VMへマウントされているDrive 1/2を登録・検査・移行保存してはならない。
  現在のDrive 2が非RA媒体、別ゲーム、未マウントでも、選択ゲームの正常な
  起動プロファイルを読む処理を失敗させてはならない。

### 2.3 RA未使用・通信不能時の動作

- RA mode OFFではRAのDB、ライブラリ、hash解決、作業コピー、ログイン状態、
  ネットワークに依存しない。従来のNormal経路で指定D88を直接マウントする。
- RA mode ONでも、未ログイン、ログイン失敗、起動時からの通信不能時は
  RAサーバー応答を待たず、ローカル登録と作業コピー生成が成功すれば
  Offline sessionでDrive 1、2をマウントする。
- Hardcore session中のDrive 2変更で通信できない場合、当該hashの同一RA Game IDが
  信頼できる保存済み検証結果にあれば、再通信せずHardcoreを維持してマウントする。
- Hardcore session中に未検証のDrive 2 hashを通信不能で検証できない場合は、
  ディスク操作自体を拒否しない。Hardcore評価を停止してsession限定Offlineへ移行し、
  ローカル登録・検査後にDrive 2をマウントする。Hardcoreのまま未検証媒体を通さない。
- 通信不能はD88のローカルOpen、bank切替、eject、`Open Both`、CLI、
  drag-and-dropを待ち続けさせる理由にしない。

## 3. 媒体操作

- Drive 1の初回起動または別ゲームへの変更は、新しいanchorとして識別し直す。
- Active中にDrive 1を同一ゲームの別D88へ変更する場合だけ、
  `rc_client_begin_change_media()`成功後にVM媒体を交換する。
- 同一D88内のbank切替ではRA媒体変更APIを呼ばない。
- Drive 2の挿入、bank切替、取り出しではRA active media変更APIを呼ばない。
  Hardcoreの挿入・bank切替で必要なhash所属検証APIは呼び得る。
- `Open Both`はbank 0をDrive 1、bank 1をDrive 2へ割り当てる単一トランザクションとする。
- Library、M3U、CLI、drag-and-drop、file menuは同じ調停処理を通す。
- drag-and-dropでDrive 1のRA媒体変更が非同期になる場合、Reset要求を
  transactionに保持し、RA承認と新媒体のVM commit成功後に実行する。
  旧媒体をResetしてから新媒体をマウントしてはならない。
- VMマウント失敗時は対象Drive構成を復元する。Drive 1のRA媒体変更後に失敗した場合だけ
  旧hashへRA rollbackする。

### 3.1 規範となる状態遷移表

実装上の判断は`TransitionRaDisk()`だけに集約する。入口ごとのUIコードは、現在状態、
trigger、guardを渡し、返されたaction以外を独自に選んではならない。

| 現在状態 | trigger | guard | action | 次状態 |
|---|---|---|---|---|
| Normal（RA OFF） | 全ディスク操作 | 常時 | RA処理なしで直接ローカル操作 | Normal |
| Offline | Drive 1/2 mount・bank・eject | ローカル検査成功 | 通信せずローカル操作 | Offline |
| Ready | Drive 1 mount | － | Drive 1をmountし、anchor識別開始 | Starting |
| Starting | Drive 2 mount/bank | Casualか検証済みhash、同一local game | Drive 2をmount。active hashは不変 | Starting |
| Starting | Drive 2 mount/bank | Hardcore、未検証、通信可能、同一local game | hash所属検証開始。VM mountは保留 | Pending |
| Starting | Drive 2 mount/bank | Hardcore、未検証、通信不能、同一local game | Offlineへ移行してmount | Offline |
| Starting | その他の変更/eject | － | busyとして拒否 | Starting |
| Casual Active | Drive 2 mount/bank | 同一local game | Drive 2をmount。通信・active media変更なし | Casual Active |
| Casual Active | Drive 2 mount/bank | 別local game | 拒否 | Casual Active |
| Hardcore Active | Drive 2 mount/bank | 現在Game IDで検証済み | Drive 2をmount。active hashは不変 | Hardcore Active |
| Hardcore Active | Drive 2 mount/bank | 未検証、通信可能 | hash所属検証開始。VM mountは保留 | Pending |
| Hardcore Active | Drive 2 mount/bank | 未検証、通信不能 | Offlineへ移行してmount | Offline |
| Casual/Hardcore Active | Drive 1 bank | 同一D88 container | ローカルbank変更。active hashは不変 | 同一状態 |
| Casual/Hardcore Active | Drive 1 mount | 同一hash | ローカルmountのみ | 同一状態 |
| Casual/Hardcore Active | Drive 1 mount | 同一local gameの別D88 | RA media change承認を開始。VM mountは保留 | Pending |
| Casual/Hardcore Active | Drive 1 mount | 別local game | 新anchorとしてcold launch | Starting |
| Pending | 全媒体変更/eject | － | busyとして拒否 | Pending |

`Pending`にはDrive 1 media changeとDrive 2 hash検証の両方を含める。Drive 2検証の
成功actionはVMのDrive 2だけを変更する。検証の結果が別Game IDまたは未識別なら旧媒体を
維持して拒否する。通信/API不能ならHardcoreを維持せず、Offlineへ移行した後で対象媒体を
mountする。

### 3.2 副作用の実行順序

1. D88形式・bank範囲をローカル検査する。
2. RA ONの場合だけライブラリ登録と作業コピー解決を行う。RA OFFではこの段階自体を通らない。
3. 状態遷移表からactionを一つ決定する。
4. `VerifyAuxiliary`または`ChangeAnchorMedia`ではVMを変更せず、非同期結果を待つ。
5. 成功後にVMへcommitし、その後に起動プロファイルを更新する。
6. Drive 2検証成功時は`rc_client_begin_change_media()`、active hash更新、session再開始を行わない。
7. 通信不能fallbackは先にsessionをOfflineへ落とし、その後にローカルmountする。

## 4. 実装

1. Drive役割と処理結果を返す単一policyを追加した。
2. `OpenDiskFromUser()`をpolicy結果に従う調停役へ整理した。
3. Drive 2専用のhash所属検証APIをactive media変更APIと分離して復元した。
4. Library起動ではanchorだけをRAへロードし、Hardcoreの割当済みDrive 2は検証成功後に開く。
5. Drive 1のmedia change、rollback、登録時hash、作業コピー保護を維持した。
6. file menuのディスク項目とplaylist項目のID衝突を解消し、入口のroutingを共通化した。
7. RA ON時、補助DriveのVMマウント成功後に起動プロファイル保存だけが失敗しても、
   成功済みのマウントをrollbackしないようcommit条件を分離した。

### 4.1 2026-08-30時点の再修正対象

Drive 2がマウントされない不具合の修正時に、Drive 2専用のhash所属検証まで
削除した。これは削除範囲が広すぎる。Drive 2をRA active mediaとして扱う状態や
`rc_client_begin_change_media()`依存は復活させず、Hardcore用の「現在のRA Game IDに
属するhashか」という副作用のない検証だけを復元する。

またdrag-and-dropの呼び出し側は、非同期媒体変更の開始をマウント完了と
扱って即座にResetしている。Reset実行を新媒体commit後へ移す。

### 4.2 Drive 2単独Open不具合の直接原因

`DiskSpec`のフィールド順が`path, bank, drive`である一方、全呼び出し元は
`path, drive, bank`の順で初期化していた。このためDrive 2メニューの指定
`{path, 1, 0}`が「Drive 1へbank 1を開く」と解釈され、Drive 2には何も
マウントされていなかった。

`DiskSpec`を`path, drive, bank`の明示的なコンストラクタで生成する型へ変更し、
Drive 2単独Openが常に`drive=1, bank=0`として伝播するよう修正した。この不具合は
RA処理より前の引数解釈で発生していたため、RA OFF、未ログイン、Casual、Hardcoreの
すべてで同じ症状になっていた。

### 5.2 quasi88調査結果

quasi88のRA連携はDrive 1挿入だけをゲーム識別のanchorとして扱い、Drive 2挿入と
D88 bank変更を通常のローカル操作として分離している。この境界は本仕様の
「Drive 1だけがactive mediaを所有する」根拠として採用した。一方、quasi88は旧RAIntegrationの
全ファイル識別を使っており、現行rcheevosでの非同期Drive 2 hash所属検証、通信不能fallback、
二ドライブcommitの参考実装にはならないため、その部分は本状態遷移表を規範とした。

## 6. 完了条件

Drive 2がRAライブラリと起動プロファイルに保存され、ライブラリ起動で
復元されること。HardcoreではDrive 2が現在のRA Game IDの媒体と検証された
後にマウントされること。その検証でDrive 1のactive hashやRA sessionを変更しないこと。
Casual／OfflineにHardcore専用検証を強制せず、検証済みhashに不要な再通信をしないこと。
RA mode OFFはRA機能と通信に完全に非依存であること。RA mode ONで通信不能でも
Offline sessionへの明示的な移行によりディスクマウントを阻害しないこと。
drag-and-dropの非同期Drive 1媒体変更は新媒体commit後にResetし、
古い媒体を先にResetしないこと。

Drive 2ルーティングとマウントは
`ee001f2 Fix RA disk mount state machine and Drive 2 routing`を基礎とし、Hardcore用Drive 2
hash検証、全入口の調停、通信不能fallback、drag-and-drop Reset commit順序を
上記の境界で再実装した。
