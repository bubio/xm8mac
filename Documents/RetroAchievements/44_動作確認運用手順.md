# 【廃止】動作確認運用手順

> **廃止（2026-09-02）**: この文書は旧仕様に対する運用記録であり、仕様、実装判断、
> 自動試験、受入試験の根拠として参照してはならない。媒体処理とその検証基準は
> [45_RA統一媒体状態仕様と検証基準.md](45_RA統一媒体状態仕様と検証基準.md) と
> [46_RA統一媒体動作確認運用手順.md](46_RA統一媒体動作確認運用手順.md) を参照する。
> この文書のCasual／Hardcore別の媒体ケース、AG番号、チェックリストは再利用しない。

基準日: 2026-09-01

## 1. 目的

変更後の確認を、次の3層に分けて実施する。

1. **自動テスト**: build、単体テスト、統合テストで機械的に確認する。
2. **開発エージェント実働テスト**: Codexが実際のbuildを起動し、GUIと実行状態を確認する。
3. **ユーザー手動テスト**: 実ディスク、実アカウント、通信断、macOSの保護UIを含む最終受入を行う。

「テスト済み」とだけ記録してはならない。各ケースについて、実施層、build、RA mode、
ネットワーク状態、入力方法、結果を区別して記録する。

## 2. 責任分界

| 層 | 主担当 | 確認対象 | 確認できないもの |
|---|---|---|---|
| 自動テスト | Codex／CI | RA対応build、policy、状態遷移、DB、hash、HTTP fake | 実際の画面、実キーチェーン、実通信、実ディスクの体感動作 |
| エージェント実働テスト | Codex | 実buildの起動、SDL GUI、mouse／keyboard、メニュー遷移、表示、マウント結果 | macOSパスワード入力、ユーザーしか判断できない実ゲーム挙動、Mac全体の通信断中の操作 |
| ユーザー手動テスト | ユーザー | 実アカウント、キーチェーン、実媒体、通信断、長時間実行、最終操作感 | 内部policyの全分岐網羅 |

自動テストだけでGUIの成功を宣言してはならない。エージェント実働テストだけで
Hardcore準拠や通信不能時の全分岐を宣言してはならない。ユーザー手動テストだけで
回帰がないと宣言してはならない。

## 3. 共通の事前確認

すべての実働テスト前に次を確認する。

- テスト対象のcommitまたは未commit差分を記録する。
- 起動するアプリの絶対パスを記録する。
- 他のXM8プロセスが起動していないことを確認する。
- RA mode OFF/Casual/Hardcore、ログイン状態、ネットワーク状態を記録する。
- 使用するD88とDrive 1/2の期待構成を先に決める。
- ユーザー管理のD88、`setting.bin`、`state0.bin`、RA DBを削除、移動、置換しない。
- 不具合回避のための自動バックアップ、壊れたstateの退避・復元処理を勝手に追加しない。
- 認証token、パスワード、D88内容、ユーザーのローカルパスを診断ログへ出さない。

macOS版はbuild場所が違っても、通常は同じ
`~/Library/Application Support/retro_pc_pi/xm8/`を使用する。別のbuildを起動するだけでは
設定、automatic state、RAライブラリは隔離されない。このため、Codexはユーザーへ知らせずに
アプリを多重起動したり、設定領域を初期化したりしてはならない。

## 4. 第1層: 自動テスト

### 4.1 標準実行スクリプト

通常はリポジトリrootから`verify_ra.sh`を使用する。変更範囲に対応する最小scopeを選ぶ。

```sh
scripts/verify_ra.sh --scope ui
scripts/verify_ra.sh --scope disk
scripts/verify_ra.sh --scope state
scripts/verify_ra.sh --scope auth
scripts/verify_ra.sh --scope full
```

| scope | 主な対象 |
|---|---|
| `ui` | menu、overlay、mouse／keyboard、文字表示 |
| `disk` | D88、Drive 1/2、Library起動、媒体policy |
| `state` | 起動・終了、state、session、frame callback |
| `auth` | credentials、HTTP、login、service |
| `full` | 複数領域にまたがる変更、Hardcore policy、release確認 |

実行対象はRA対応buildだけとし、既定で`build-ra`を使用する。
`XM8_ENABLE_RETROACHIEVEMENTS=OFF`のRA無効buildは使用せず、自動テスト、GUIテスト、
ユーザー手動テストの対象に含めない。Normal回帰はRA対応build内の`RA mode OFF`で
確認する。この2つを「RA OFF」という同じ語で扱ってはならない。

```sh
scripts/verify_ra.sh --scope ui \
  --ra-build-dir build-ra
```

実行前にcommandだけ確認する場合は`--dry-run`を付ける。結果は既定で
`/tmp/xm8-validation-<scope>-<日時>.md`へ保存される。保存先は`--report`で変更できる。

スクリプトのPASSは自動テスト層だけの結果である。GUIとユーザー手動確認を含まないことは
生成reportにも明記する。

### 4.2 手動で自動テストを実行する場合

RA共通コード、UI接続、ディスク、state、認証、通信を変更した場合は、最低限次を行う。

```sh
cmake --build build-ra --parallel 4
ctest --test-dir build-ra --output-on-failure
git diff --check
```

macOSの認証テストを実行ファイルから直接起動する場合は、実キーチェーンを使わないよう
次の環境変数を必ず付ける。`ctest`には同じ設定がtest propertyとして登録されている。

```sh
env XM8_RA_CREDENTIALS_TEST_MEMORY=1 ./build-ra/ra_service_test
```

この環境変数はテスト専用であり、実アプリのキーチェーン確認には使用しない。

### 4.3 RA mode OFF回帰

Normal動作はRA対応buildの`RA mode OFF`で確認する。自動テストではRA対応build内の
Normal共通testとRA mode OFF policyを実行し、実際のメニュー、ディスク、state、Full Speedは
第2層または第3層で確認する。

### 4.4 変更範囲別の必須項目

| 変更範囲 | 必須の自動確認 |
|---|---|
| 文書だけ | `git diff --check`、リンクと記述の整合確認 |
| RA policy／状態遷移 | RA対応buildの全test、対象policy test |
| UI／menu／入力 | RA対応app build、RA mode OFF回帰、overlay/menu関連test |
| Drive／D88／Library | media policy、probe、store、launch、multi-image、eject関連test |
| state／起動／終了 | state、session state、callback、RA対応app build |
| 認証／HTTP／接続監視 | service、credentials、HTTP、session関連test |
| Hardcore制限 | operation policy、pause、frame callback、state、media関連test |

### 4.5 合格条件

- configureとbuildが終了code 0で完了する。
- 対象testがすべてpassする。
- RA対応buildの自動テストと、同build内のRA mode OFF/Casual/Hardcoreの必要な実働経路を区別する。
- skip、未実施、環境理由の失敗をpassとして数えない。
- 既知の失敗がある場合は、今回の変更との無関係を根拠付きで記録し、最終結果を
  「全成功」と表現しない。

## 5. 第2層: Codexによる実働GUIテスト

### 5.1 実施可能な操作

Codexは、ユーザーの許可された範囲で次を実施する。

- 指定された`.app`を起動する。
- 起動中processの実行ファイルpathを確認する。
- SDL画面上のmenuをmouse、keyboardで操作する。
- RA mode OFF/Casual/Hardcore、Library、Game Detail、START、Drive menu、Full Speed表示を確認する。
- Drive 1/2の表示、bank、RA status、Offline表示を確認する。
- 必要な場合だけ、機密情報を含まない一時診断ログを追加し、確認後に完全に撤去する。

Codexは次を自動で行わない。

- macOS login passwordまたはキーチェーンpasswordの入力。
- RA password、tokenの取得、表示、保存、ログ出力。
- Wi-Fi、Ethernet、VPNを勝手に切断する操作。
- `state0.bin`、設定、RA DB、D88の削除・置換。
- ユーザーの指示なしにD88原本へ書込みを伴う操作。

Codex自体がインターネット経由で動作するため、Mac全体の接続を遮断すると、その間は
CodexによるGUI操作、状態確認、会話、記録を継続できない。実ネットワーク切断試験を
「ユーザーが切断し、そのままCodexが確認する」手順にしてはならない。

### 5.2 macOSキーチェーン確認

新しいbuild、署名状態が変わったbuild、実行ファイルpathが変わったbuildでは、保存済みRA tokenを
読み出す際にmacOSがキーチェーンのpasswordまたはアクセス許可を要求することがある。

1. Codexは保護ダイアログを検出した時点で操作を停止する。
2. ユーザーへ、対象アプリ名と要求内容を確認してもらう。
3. passwordはユーザー自身がmacOSのダイアログへ入力する。チャットへ送らない。
4. `許可`、`常に許可`、`拒否`の選択はユーザーが判断する。Codexは自動選択しない。
5. ユーザー操作後、CodexがGUIテストを再開する。

キーチェーン要求が未処理、拒否、timeoutになった場合、RAログインの確認結果は
**失敗**ではなく**ユーザー操作待ち／未実施**と記録する。その状態でRA実通信成功を
宣言してはならない。

### 5.3 基本smoke test

変更の影響範囲に応じ、次から必要なケースを実施する。

| ID | 条件 | 操作 | 合格条件 |
|---|---|---|---|
| AG-01 | RA mode OFF | RA対応app起動、Main menu表示、終了、再起動 | crashせず、意図しないRA通信・RA待ちがない |
| AG-02 | RA mode OFF | Drive 1とDrive 2を個別にOpen、bank変更、Eject | 選択したDriveだけが変わり、GUIが固まらない |
| AG-03 | RA mode OFF | RA LibraryからGame Detailを開き、STARTをmouseで押す | 1回のclickで起動する |
| AG-04 | RA mode OFF | AG-03をkeyboard Enterでも実行 | mouseと同じ起動結果になる |
| AG-05 | RA ON Casual | Library、Game Detail、START、Drive表示を確認 | profileどおりに起動し、RA statusが矛盾しない |
| AG-06 | RA ON Hardcore | Full Speedを選択、Drive 2を含む保存profileを起動 | Full Speedは禁止され、Drive 2は規定の検証後にmountされる |
| AG-07 | RA通信だけを遮断できるtest hookがある場合 | LibraryまたはD88から起動 | 無限待ちせずOffline sessionでゲームが起動する |
| AG-08 | 入力変更 | 同じ画面をmouseとkeyboardで操作 | 表示されている項目と実際のhit targetが一致する |
| AG-09 | RA ON Casual／HardcoreでゲームAがActive | 別ゲームBの1bank raw D88をdrag-and-drop | cold reset後にゲームBのanchor識別が開始し、ゲームAのGame ID／hash／実績評価sessionが残らない |

AG-06のDrive 2確認には、ユーザーが指定した3bank実媒体
`/Volumes/CrucialX6/roms/PC88/TEST/Ys 1 PC88 - English Translation/Ys1_English_RA.d88`
を使用できる。Libraryの`Ys`をSTARTし、Drive 1=`DISK_A`、
Drive 2=`DISK_B`になることを確認する。実行前後のSHA-256も比較する。

AG-07は、Codexとの接続を維持したままXM8のRA通信だけを失敗させる、明示的で安全な
test hookまたはfake transportが存在する場合だけ実施する。その仕組みがない現在の実buildでは
`NOT RUN`とし、実通信断は第3層のユーザー手動テストで確認する。firewall、hosts、VPNなどを
即席の代替手段として勝手に変更しない。実D88が必要なケースは、ユーザーが明示した媒体だけを
使用する。

### 5.4 実働テストの記録

最低限、次を残す。

```text
Build: /absolute/path/to/xm8.app
Commit/diff: <commitまたは差分の説明>
Case: AG-xx
RA: OFF / Casual / Hardcore / Offline
Network: reachable / unavailable / not controlled
Input: mouse / keyboard / touch / controller
Media: fixture / ユーザー指定実媒体 / なし
Result: PASS / FAIL / BLOCKED / NOT RUN
Evidence: 表示、mount結果、非機密ログ、再現手順
```

## 6. 第3層: ユーザー手動受入テスト

ユーザー手動テストは、Codexが自動テストと実働テストの結果、残る確認項目、起動するbuild pathを
提示してから開始する。ユーザーへ「一通り確認してください」とだけ依頼してはならない。

### 6.1 Normal／RA mode OFF（RA対応build）

- [ ] ネットワーク接続ありで通常起動できる。
- [ ] ネットワーク接続なしでも待たされず通常起動できる。
- [ ] Drive 1、Drive 2を個別にOpenできる。
- [ ] `Open Both`で期待する2 disk構成になる。
- [ ] bank切替とEjectが対象Driveだけに反映される。
- [ ] M3U、drag-and-drop、Library STARTが起動する。
- [ ] Library STARTをmouseとEnterの両方で実行できる。
- [ ] Full Speedが従来どおり使用できる。
- [ ] Normal stateのSave／Load、終了後の再起動が従来どおり動く。

### 6.2 RA Casual

- [ ] キーチェーン許可後、保存済みtokenでログインできる。
- [ ] Drive 1 anchorとDrive 2が保存profileどおり復元される。
- [ ] Drive 2操作でRA active hashやgame sessionが変わらない。
- [ ] Active中に別ゲームの1bank raw D88をdrag-and-dropすると、旧sessionを終了して
  新しいDrive 1 anchorの識別へ移行する。
- [ ] Library STARTをmouseとEnterの両方で実行できる。
- [ ] state Save／LoadがRA Casual用導線だけで使用できる。
- [ ] 起動時通信不能ではOffline sessionへ移行し、disk mountを妨げない。

### 6.3 RA Hardcore

- [ ] 起動時にDrive 1 anchorの識別が終わるまでVMが開始しない。
- [ ] 起動profileのDrive 2が同じRA Game IDと検証された後にmountされる。
- [ ] Drive 2検証でactive hash、RA session、実績評価対象が変わらない。
- [ ] Full Speedは使用できない。これは不具合ではなく仕様である。
- [ ] デバッグ用の手動Saveは実行できる。Hardcore中のLoad、通常用途またはautomaticの
  state作成は実行されない。
- [ ] 未検証Drive 2を通信不能で検証できない場合、Hardcoreのまま通さず、
  Offline sessionへ移行してからmountされる。
- [ ] 検証済みDrive 2は不要な再通信なしでmountされる。
- [ ] Active中に別ゲームの1bank raw D88をdrag-and-dropすると、旧Game ID／hashを
  維持せず、新anchor識別とcold resetを行う。
- [ ] D88原本が試験前後で変更されていない。

### 6.4 起動・終了・automatic state

- [ ] 通常終了後に再起動できる。
- [ ] `state0.bin`が存在する通常環境で再起動できる。
- [ ] Library起動後に終了し、再度アプリを起動できる。
- [ ] state読込失敗時に無反応や起動不能にならず、理由が確認できる。

`state0.bin`を削除すれば起動する、という結果だけで合格にしてはならない。削除前の状態を
勝手にバックアップして継続する処理も追加しない。原因をログと再現条件から特定する。

### 6.5 実ネットワーク切断試験の進め方

Mac全体の接続を切る試験はユーザーが単独で操作する。Codexは切断前に、対象build、開始状態、
操作手順、期待結果を提示する。

1. Codexから手順を受け取り、必要ならこの文書をローカルで開いておく。
2. ユーザーがインターネット接続を切る。
3. ユーザーがXM8を起動し、対象のLibrary起動またはDrive操作を行う。
4. Offline session表示、起動可否、Drive 1/2、待ち時間、エラー表示をユーザーが記録する。
5. XM8を残したまま確認を続けるか、終了するかは事前手順に従う。
6. ユーザーがインターネット接続を復旧する。
7. Codexへ結果を伝え、必要なら復旧後にログや画面状態を確認する。

切断中にCodexから追加指示が届くことを前提にしない。想定外の画面になった場合は、破壊的な
回避操作をせず、画面と操作を記録して接続を復旧する。

## 7. 変更種別ごとの実施レベル

| 変更 | 自動テスト | Codex実働 | ユーザー手動 |
|---|---|---|---|
| 文書、commentのみ | 必須 | 原則不要 | 原則不要 |
| 純粋policy、parser、DB query | 必須 | 影響する代表経路 | release前または実媒体依存時 |
| menu、描画、mouse／keyboard | 必須 | 必須 | 最終受入で必須 |
| Drive、Library起動、D88 | 必須 | fixtureまたは指定媒体で必須 | 実媒体で必須 |
| state、startup、shutdown | 必須 | 必須 | 既存ユーザー環境で必須 |
| 認証、Keychain、実HTTP | 必須 | 保護UI直前／直後まで | password・許可操作を含め必須 |
| Hardcore制限 | 必須 | 代表操作を必須 | 実アカウント・実媒体で必須 |
| 通信不能fallback | fake通信で必須 | RA通信専用test hookがある場合だけ実施 | 実ネットワーク切替で必須 |

## 8. 不具合発生時の手順

1. 操作を繰り返す前に、build path、画面、入力、RA mode、network、mounted diskを記録する。
2. keyboardでは動くがmouseでは動かない、RA mode OFFだけ失敗する、Drive 2だけ失敗する、など
   条件を1つずつ分離する。
3. 必要なら機密情報を含まない一時ログを追加する。
4. ユーザーに依頼する操作は1回分を具体的に示し、実行後はアプリを閉じるか残すかも指定する。
5. 原因確定前にstate削除、backup fallback、ディスク再登録など別の回避策を実装しない。
6. 修正後は失敗した層だけでなく、自動テストから順に3層を再実施する。
7. 一時ログ、診断用UI、試験ファイルを最終buildへ残さない。

## 9. 完了報告の形式

完了報告は次の形式にする。

```text
自動テスト:
- RA対応build: PASS / FAIL / NOT RUN
- ctest: n/n PASS
- git diff --check: PASS / FAIL

Codex実働テスト:
- AG-xx: PASS / FAIL / BLOCKED / NOT RUN
- 使用build: /absolute/path/to/xm8.app
- 未実施理由: あれば記載

ユーザー手動テスト:
- UM相当項目: PASS / FAIL / PENDING
- ユーザー操作待ち: Keychain、network、実媒体など

残件:
- なし、または具体的な未確認事項
```

完了条件は、変更に必要な全ケースがPASSであること、または未実施項目とその理由が明示され、
ユーザーが残件として認識していることである。

## 10. Codexスキルからの実行

個人用Codexスキル`xm8-validation`を使用する場合は、次のように依頼する。

```text
$xm8-validation で現在の変更を検証してください。
```

スキルは本文書を最初に読み、差分からscopeを選び、`scripts/verify_ra.sh`、必要なGUI確認、
ユーザー手動確認の順に進行する。スキルは実行の調停役であり、仕様やチェックリストの
保存場所ではない。本文書とスキルが矛盾する場合は本文書を優先し、スキルを修正する。
